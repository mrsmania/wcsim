One run at a time: what it changes in the code

This is the one item in this set that is not chrome, so it is worth being exact about. Today two runs really can be live at once, and it is not hypothetical: a World Cup lives in the game state, a Cup Run in wcsim_run_v1, and handleStartGroup (App.tsx:509) never clears the run. So starting a Cup Run, returning home, and kicking off a World Cup with the same XI leaves both in progress, which is why the launcher takes both a worldCupRoute and a cupRunInProgress prop.

TodayWith one run
Up to three resume rows: World Cup, Cup Run, half-built XI (the third is already suppressed when either of the first two exists). Exactly one Continue, whatever state it is in: mid-build, group, knockout or Cup Run.
Building a fresh XI clears the run (saveRun(null) at four call sites) but not the tournament, so a stale group can outlive the XI that played it. One kickoff clears the other, in one place, and "build a new XI" confirms first.
Two engines, two outcome models, two once-per-run sticker guards, two run-end panels. The switch makes One-off a Cup Run at Base with no boosts, so there is one run to be in progress at all.
Sequencing The rule is functionality, and item 27 is chrome, so it does not have to land together with the nav. But it points the same way as the engine convergence the audit lists as unowned, and it deletes the multi-resume list that the cover would otherwise have to hold. Worth deciding before the nav is built, since the cover's shape depends on the answer.
