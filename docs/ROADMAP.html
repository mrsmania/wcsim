01 Challenges / Mandates Something to aim at in Career Mode, instead of Prestige just piling up. Career ▸

The highest-value gap. The career layer has no goals: you play, you earn Prestige, you buy perks, and that is the entire loop. Challenges give a reason to attempt a particular kind of run rather than the same strongest one.

  • Renewable objectives checked against the finished RunState: win at Ascension III, win with an XI averaging under 80, clean-sheet the knockouts, win with a single-nation XI.
  • They pay in Prestige and in trophy-cabinet entries, which is also what would give the cabinet (item 06) something to hold.
  • Data model and example challenges already drafted in docs/career-depth-spec.md, "Future ideas / E".
  • Pairs well with accounts: progress is per account, so it follows you between devices.

Decision first: are challenges permanent, rotating, or a mix? Then pick the opening handful.

03 More World Cups and collectibles Extend the dataset backwards from 1990: 1986, 1982, and earlier. Content ▸

The dataset covers 1990 to 2022, all nine fully researched. Collectibles grow for free, since collectibility is derived from rating via STICKER_TIERS.

  • Method notes from the 1990-2002 round apply: identical name spellings across tournaments for the same person (personId is the name slug), distinct people must have distinct names, ratings are that-tournament strength on 60-99.
  • Field sizes shrink going back (24 teams in 1982 and 1986, 16 in 1970-1978), so check the group draw and any "32 nations" assumptions first.
  • Period identities keep their own codes, as Soviet Union, Czechoslovakia and Yugoslavia already do.
  • Remember the server: after any rating change run npm run gen:collectibles then npm run push:collectibles. npm run checks fails while the seed is stale.

Next step: do 1986 end to end as the template for the rest.

16 Apply migration 0010 on the NAS The one-trip bank is written and tested; the server has not had it yet. Hands-on ▸

Item 08's fix is in the repo but not on the live database, because applying it needs LAN or VPN access to the NAS. Until it is applied the client keeps using the old three-round-trip path, which is exactly today's behaviour - the change was built to work in either deploy order, so nothing is broken while this sits here.

  1. Apply it from any machine that can reach the NAS - the same LAN or VPN requirement as push:collectibles, and the same route (Studio's pg-meta endpoint, service key from dkr/.env). It is one transaction, so a failure leaves nothing behind, and --dry-run shows what would be sent. 
    npm run push:sql -- supabase/migrations/0010_finish_run_one_trip.sql
    Pasting the file into Studio's SQL editor does the same thing if you would rather watch it go in.
  2. Check the function is reachable as the client sees it, not just as the owner: PostgREST needs the grant, and a missing one shows up as the client quietly staying on the old path. Expect true. 
    npm run push:sql -- --query "select has_function_privilege('authenticated',
  'finish_run_v2(text,text[],boolean,text,integer,text,integer)', 'execute')"
  3. Bank a run signed in and confirm the haul appears without the pause. The browser's network panel should show one finish_run_v2 call and no profiles / album_stickers reads after it.

If it has to be rolled back: nothing to undo. Dropping finish_run_v2 puts the client back on the old path on its next bank, since that is the fallback it already carries - but the wrapper finish_run delegates to v2, so re-apply 0009 in that case to restore its body.

supabase/migrations/0010_finish_run_one_trip.sql, docs/nas-setup.md

15 Point GoTrue at the new sign-in email The template is written and deployed; the server still sends the stock one. Hands-on ▸

The mail itself is done (2026-08-18) and lives in the repo, deployed with the site: public/email/otp.html plus public/email/logo.png. It is deliberately plain, modelled on a reference the owner supplied: the trophy tile and wordmark, one line, the six digits, and a line saying to delete it if it was not you. No greeting, no sign-off, no unsubscribe footer - a transactional mail nobody subscribed to needs none of them.

Settled while building it. A real copy button is impossible (mail clients run no JavaScript), so the code is large, letter-spaced and selectable, which is what makes tap-and-hold work on a phone. The logo is a hosted PNG rendered from the app's favicon SVG, because Gmail drops SVG and blocks data: URIs in images; the wordmark beside it is text, and the image carries alt="", so with images off the header still reads without alt text spilling out of a 40px box. Tables and inline styles throughout, and web-safe font stacks: the mail borrows the palette rather than pretending to match Archivo and Spline Sans Mono, which mail clients would refuse anyway.

What is left needs the NAS, which is why this stays open:

  1. Set four values in dkr/.env. The same template serves both cases - a returning address gets the magic-link mail, a new one gets the signup confirmation - so leaving either on the stock template means half the players still see it. 
    GOTRUE_MAILER_SUBJECTS_MAGIC_LINK=Your World Cup Simulator code
GOTRUE_MAILER_SUBJECTS_CONFIRMATION=Your World Cup Simulator code
GOTRUE_MAILER_TEMPLATES_MAGIC_LINK=https://mrsmania.github.io/wcsim/email/otp.html
GOTRUE_MAILER_TEMPLATES_CONFIRMATION=https://mrsmania.github.io/wcsim/email/otp.html
  2. Restart the auth container and request a code from the game.
  3. If it still looks stock, suspect the fetch rather than the template: GoTrue pulls the template over HTTPS as it sends, and falls back to its built-in default when that fails. 
    curl -sI https://mrsmania.github.io/wcsim/email/otp.html
    from the NAS settles it.

Afterwards: editing the mail is a push to main and the Pages deploy, with no container restart - only these env vars need one.

  • 10 follow-up: a move can rotate three or more. Done 2026-08-18, after the user asked why an interchangeable front three could not be switched round. Pairwise trades already worked and had shipped, so the report looked wrong at first - but the narrow case behind it is real: where NO pair can trade, a rotation still can. From the dataset, Knoflicek [LW,ST] at LW, Burruchaga [AM,RW,ST] at ST, Donadoni [LW,RW,AM] at RW - each pairwise swap correctly refused (nobody can play the other's slot), yet rotating all three one place round is perfectly legal, so the front three read as stuck. Swept over every formation and 40 random XIs each: 8,801 legal moves, 821 of them (9.3%) reachable only by a rotation.
    canMove became planMove, which returns the whole resulting placement and finds it with the standard bipartite augmenting path (Kuhn): put the mover in his target, then re-place whoever he displaced, recursing through whoever THAT displaces. Each slot is considered once per search, which keeps it linear (~15 us even with eleven players who can all play everything) and finds the smallest rearrangement rather than reshuffling the XI. The empty-slot move and the straight trade are the same rule with chains of one and two, so nothing that worked before changed. MOVE_PLAYER now just stores what planMove returns, so the reducer never has to know the shape of the chain. The badge stops promising a straight trade when it is not one: a rotate glyph and "take X's spot, rotating N players". Verified over 8,801 plans that every result is a valid line-up with nobody dropped or duplicated, plus the rotation and a plain trade driven in a browser.
    Follow-up the same day: while a player was held for a move, the budget market's "next position to shop" slot kept its pulsing white "+" even though it was inert unless it happened to be a destination - the loudest thing on the pitch, ignoring every click. That highlight now steps aside for the duration of a move (a quiet dashed circle), while a genuine empty destination still pulses. Both halves checked in a browser: no inert pulse survives with a player held, and an empty destination still lights up and accepts the move.
    And a second: the two selections now override each other both ways. Taking a card out of the squad list or the market already dropped a move in progress, but the reverse did nothing at all - with a card in hand, tapping a placed player was inert, so the only way out was to put the card back first. Now that tap picks the player up and drops the card (SELECT_PLAYER takes null). One precedence rule survives, and it is not an asymmetry: a slot the held collectible can swap into keeps the swap, since that is the specific thing that card is for. The cancel effect had to stop watching the selection at the same time, or a move would have cancelled itself the instant it cleared the card. Checked in a browser both ways, and that a held collectible still shows "swap in for" on the two slots it fits while the other badges offer a move.
  • 10 A placed player can move within his position range. Done 2026-08-18. Tap his badge with empty hands and the slots he can take light up: empty ones as a "+", team-mates he can trade places with as an amber swap badge. Tapping him again puts him back, and while he is held every other badge is inert, so the only things clickable are the destinations and the cancel. A player with nowhere to go is not clickable at all - found by driving it in a browser, where the first badge picked up was a single-position full-back who lit nothing and left the gesture a dead end. A trade needs BOTH halves to fit: the occupant has to be able to play the slot being vacated, or the pair is refused rather than quietly producing an invalid line-up. A held card (a drawn squad card or a market player) suppresses the whole thing, so placement and collectible-swap targets keep the pitch to themselves.
    The trap the item warned about is handled and now has a test with teeth: eligibility reads the player's whole positions list as a set, never positions[0], since placedPlayers hands downstream code copies with the filled slot promoted to the front - keying off the first entry would collapse a player's range to wherever he happens to be standing and shrink it again with every move. npm run checks now walks a player back and forth eight times and fails if what he is offered ever changes; reintroducing the bug on purpose made it fail, so the check is known to catch it. The reducer moves the player objects as they are and never writes back a reordered copy, and the XI keeps the same eleven people, so usedPersonIds and the phase are untouched. Behind FEATURES.movePlayers; false makes a placed badge inert again.
  • 08 Banking a run costs one round trip, not three. Done 2026-08-18, after profiling rather than guessing - the four candidates had four different fixes and three of them were innocent. Not the deliberate wait: BANK_WAIT_MS caps how long the "Draft a new XI" button reads "Saving stickers...", while the summary renders when the promise resolves. Not the function: measured on a local Postgres running the real migrations and the real 81-row catalogue, finish_run takes 8.8 ms cold and 1.3-1.9 ms warm for a full 11-sticker haul. The write queue contributes one round trip per write already in flight. The cause was that a bank cost three sequential round trips: the call, then a state_version read, then the album plus album_stats - because the function returned only the new ids. Measured client-side against a fake transport at 100 ms/request: 302 ms idle, 502 ms behind two writes. Migration 0010 adds finish_run_v2, which returns the new ids, the version, the album rows and the stats computed in the same transaction, so the client's "the server counted, do not guess" rule is intact and the bank is one trip: 1 wave instead of 3, and 3 instead of 5 behind two writes. A new name rather than a changed return type because the client ships on push to main while the migration is applied by hand on the NAS: the client tries v2, falls back to the old path once per session if the server has not been migrated, and never falls back on a real error (PostgREST answers a missing function with PGRST202 before Postgres runs anything, so the retry is a first attempt and not a double submit). The old finish_run stays as a thin wrapper delegating to v2, so there is still one implementation. Applying it on the NAS is open item 16.

A new AccountModal wraps the unchanged AccountPanel in the shared Overlay; the masthead account button opens it (it used to open settings), and SettingsModal lost the group along with its accountEmail / onAccountChanged props, so the reload-on-sign-in handover now lives at one call site. Verified in a browser: the account button opens a dialog labelled "Sign in" whose only action is "Continue", Escape closes it, and the settings sheet opens separately with Appearance / Squad pool / Difficulty and no mention of accounts.
