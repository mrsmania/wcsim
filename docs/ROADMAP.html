03 More World Cups and collectibles Extend the dataset backwards from 1990: 1986, 1982, and earlier. Content ▸

The dataset covers 1990 to 2022, all nine fully researched. Collectibles grow for free, since collectibility is derived from rating via STICKER_TIERS.

  • Method notes from the 1990-2002 round apply: identical name spellings across tournaments for the same person (personId is the name slug), distinct people must have distinct names, ratings are that-tournament strength on 60-99.
  • Field sizes shrink going back (24 teams in 1982 and 1986, 16 in 1970-1978), so check the group draw and any "32 nations" assumptions first.
  • Period identities keep their own codes, as Soviet Union, Czechoslovakia and Yugoslavia already do.
  • Remember the server: after any rating change run npm run gen:collectibles then npm run push:collectibles. npm run checks fails while the seed is stale.

27 Navigation and click-path rework Six navigation mechanisms, none of them complete, and a 130-entry catalogue four taps in behind a collapsed panel. Same features, new chrome. UI/UX ▸

The ask (2026-08-20): keep every feature exactly as it is and rework the UI and the click paths. Nothing here is about what the app does; it is about how you get to it. The screens themselves are fine and were each designed carefully. What was never designed is the thing between them.

Ten findings, read in the code rather than remembered. The full audit with the file and line behind each one is on docs/redesign-2026/turf-flat/nav-options.html:

  • F1 Six navigation mechanisms, none of them complete. The crest links home; a footer text nav lists four of the eleven destinations; the launcher has two door cards plus up to three resume buttons; the build page has two entry cards inside a content column; the career hub holds the only link to /challenges; the tournament screens have their own crumbs. No single one of them can reach everything.
  • F2 Challenges is four taps in, behind a collapsed panel. Its only door is inside CareerHub (cupRun/CareerHub.tsx:196), on /cup-run, reached from a card that only renders on the career build page in the setup sub-view, and the hub body starts collapsed. 130 entries, effectively unlisted.
  • F3 Two doors lead to the same page. /quick-run and /career-mode are the identical 3-column build page; the route decides one CTA (App.tsx:647) and two perk values.
  • F4 /cup-run is two screens sharing one route, the career hub and the live run, with the hub collapsing to a strip mid-run. A shop and a step of play cannot be the same address.
  • F5 Navigation lives inside a content column. The album card and the "Cup Run career" card are the first two things in the build page's left column (App.tsx:947, 978), and the second disappears the moment you place a player.
  • F6 One column is four different things (setup, drawn squad or market, complete, plus the two nav cards), so nothing tells you what that region is for.
  • F7 There is no persistent "where am I". The only global signal is the active colour on an 11px mono footer nav, below the fold.
  • F8 Reset and back land inconsistently. A World Cup always resets to /quick-run even from a career build (App.tsx:564), and the crumbs, the CTAs and browser Back are three separate answers to "go back".
  • F9 Six overlays compete (settings, account, group draw, cup reward pick, trade, run-end summary), and two can be earned in the same moment.
  • F10 On a phone the pitch is in the middle, between the panel you pick from and the ratings you check, so a draft is scroll up, tap, scroll down, eleven times.

Five concepts are drawn, each over the same thirteen screens (entry, both build states, complete, group, knockout, Cup Run, career hub, album, challenges, cabinet, squads, settings) plus three phone views, so the comparison is like for like: 1 Left rail (five destinations always visible, nine of eleven one tap), 2 Five tabs (the same idea, phone-first, bottom bar), 3 Sections and sub-nav (four sections with a second row, the only one that scales past eleven screens), 4 Dashboard hub (home is a tile grid with live counters, smallest diff, weakest orientation), 5 Stage flow and drawers (a run stepper across the top, everything else opens over it and never costs you your place). The screen bodies are identical in all five files on purpose: if a body had to change to suit a nav model, the nav model would be changing the app.

Four things every concept agreed on, so they are decisions rather than options: the two launcher doors go (mode becomes a build-page control), the career hub and the live run stop sharing a route, the two nav cards leave the build page's left column, and the build page needs its phone order changed (pitch first) regardless of which nav wins.

Does Quick Run make sense at all? Asked directly while surveying this. Not as a door, yes as a switch. A Cup Run is a superset of a World Cup (they share the match sim, the group build, the draw, resolveKoTie and the live clock; a Cup Run adds boosts and Ascension), so there is nothing a Quick Run can do that a Cup Run at Base with no boost taken cannot, which makes it a strictly dominated option on the launcher. What it genuinely provides is a consequence-free way to learn the draft and a shorter session with no between-rounds decision, and neither needs a mode: one entry, one build page, and a two-state "Career run / One-off" control on it, beside formation and style. Set to One-off it keeps today's reward rules exactly (stickers bank, the career does not), so nothing is added or removed and F3 is deleted outright. Whether a one-off should pay (XP, Prestige, and the 98 of the 130 challenges a World Cup could in principle judge) is a functionality question, and it has no item of its own since item 22 was dropped; the audit's off-limits section carries it as unowned. This switch is neutral on it either way, so it can be answered later without touching the navigation again.

Next step: pick a concept, then write the four agreed decisions up as one short note with the phone build-page order included. Sequencing: worth landing before or with item 23, which touches App.tsx heavily for other reasons, and before items 04, 05 and 19, each of which adds a screen the nav will have to hold. Chrome only: no domain/, no state/, no reducer action and no feature flag, which is what makes it safe to land ahead of everything else.

23 Hygiene: dead code and refactorings A worked, wave-by-wave backlog against DRY, KISS, SoC and YAGNI. No change in functionality, just cleaner code. Blocked on item 27. Structure ▸

The ask (2026-08-20): review the whole codebase for dead code and refactorings, and produce a todo list another team can implement. The one rule is that the app that comes out plays exactly like the app that went in.

The backlog is docs/hygiene-audit.html, which is the deliverable: 105 numbered items (H1-H105) in seven waves, each naming the files, the fix, whether it is behaviour-preserving, effort and risk, plus twelve decisions that need an owner and an explicit list of what not to touch, split since 2026-08-20 into what item 27 owns and what nobody does. It was produced from six independent parallel reviews of the tree (dead weight, DRY, SoC/layering, KISS/YAGNI, type model and naming, tooling/SQL/assets), merged, with the load-bearing claims re-verified by hand.

Do not start before item 27. The navigation rework moves the same code this backlog touches: App.tsx's route branch, the mode fact derived twice (modeOfPath versus GameState.buildMode), the reset target, the two nav cards in the build page's left column, and the career hub splitting off the run screen. Doing hygiene first means doing several of them twice, and the second pass is the one that loses. The audit's off-limits section says what item 27 owns and keeps its hands off it.

It also carries what item 22 left behind. Item 22 was dropped on 2026-08-20 as framed around the wrong question, and its navigational half is item 27's now. What it also held was a set of verified findings that are now nobody's: the two tournament engines and their duplicated round shell, the two chemistry definitions (teamChemistry scores by the slot each player fills, chemistryOf by natural role, so the same XI gets two answers), the run-end sticker trigger order, the difficulty-resets-the-album rule, and whether a non-career run pays anything at all. The audit's off-limits section now lists these as unowned rather than as item 22's, because none of them is behaviour-preserving and so none of them is this backlog's to settle. Parked, not forgotten.

The waves, in execution order:

  1. Free deletions and truth fixes (H1-H35). Genuinely dead exports and props, complexity with nothing on the other side of the trade, repo weight, and eleven comments or doc claims that are no longer true. No decisions, no behaviour change.
  2. Name the constants, share the one-liners (H36-H48). Highest payoff per minute: each item removes a fact currently written down twice.
  3. Design tokens and shared UI atoms (H49-H54). The palette and caption constants already exist in index.css and matchUi.tsx and are bypassed by inline copies.
  4. Put the logic where it belongs (H55-H68). Pure computations that ended up in leaves: a Hungarian solver and a move search in Pitch, the market's query rules, budget spend computed three times, the kickoff records built in App.
  5. The type model (H69-H78). Chiefly RoundRecord as a real discriminated union, which alone deletes 18 unreachable fallbacks and a load-bearing cast, and Filled's | null arm that nothing writes.
  6. Structural extractions (H79-H90). The risky ones, one per branch: App.tsx's 15 jobs into hooks and screens, and CupRunScreen handing back the career's persistence.
  7. Harness, CI and tooling (H91-H105).

Two findings worth knowing before reading the rest. Both are in wave 7 and both are the reason to start there rather than with the code:

  • npm run checks never runs in CI. The workflow runs npm ci and npm run build, nothing else, so the 59 invariants and the collectible-seed staleness guard gate nothing automatically. Since there is no unit-test runner, that harness plus the build is the whole safety net for this backlog, and it currently depends on the author remembering.
  • The documented "serve it at another path" recipe silently produces a wrong artifact. npm run build -- --base=/ appends the argument to the last command in the && chain, so it reaches copy-404.mjs, which ignores unknown argv and exits 0. Verified empirically. The Docker option in the README is wrong for the same reason.

What the audit did not find, recorded so the next pass can skip it: no dead CSS (all 40 custom classes and 13 tokens used), no unused dependency, no dead config.ts entry, no unreferenced module in src/, no unread component prop, all 21 reducer actions dispatched, sticker art exactly in sync with the dataset in all three directions, migrations and client in sync, and zero any.

Next step: after item 27 lands, take wave 7's H91 first (checks into CI, one line) so the gate is real, then waves 1 to 3 as one pass each. Waves 4 to 6 want the decisions in the audit's Decisions table answered first, in particular which FEATURES flags retire. That table also holds D12, the four dead run_results columns, merged in from item 21 on 2026-08-20: the table itself must not be dropped (its unique (user_id, run_key) is what rejects a double submit before a sticker moves, and import_guest_progress reads it to decide whether an account is empty), only the four columns are dead weight, and reviving them would cost a finish_run_v3 and only ever cover runs from the change onward.

18 Player versus player, for signed-in accounts Build a team from your career progress and play someone else's. Details to be defined. Accounts ▸

Requested 2026-08-18, shape deliberately open. A signed-in player assembles a team from what their career has actually earned, and plays it against another player's team. The sim already decides matches from two XIs, so the match itself is the part that exists; everything around it is the design work.

What is already in place, and worth knowing before designing it: accounts and the per-account store (album, career, settings, in-progress run) are live, the match and shootout sim take two sides and are deterministic apart from their own randomness, simulateTitleOdds can rate a matchup, and the sticker economy is validated server-side because the browser talks to Postgres directly - the same reasoning will apply to anything competitive.

The questions to settle first, roughly in the order they bite:

  • What is a "team based on career progress"? The collected album only? Career budget plus perks? A separate roster you maintain? This decides whether PvP is a showcase of progress or a second economy.
  • Live or asynchronous? Asynchronous (submit a team, it plays overnight or on challenge) fits a self-hosted server and a small friend group far better than live matchmaking, and needs no realtime service - which was deliberately trimmed from the NAS stack.
  • Who validates the team? A client-submitted XI is a claim; the server has to check it against what that account actually owns, or the first thing anyone does is submit eleven 99s. This is the same problem finish_run solved for stickers and probably wants the same shape (a security definer function that reads the account's own rows).
  • Fairness. A three-year-old career against a new one is not a game. Tiers, handicaps, or a budget-equalised format all work; pick one before building.
  • What is at stake? Prestige, a ladder, a record, or nothing but bragging. Anything transferable needs anti-cheat thinking; nothing transferable is much cheaper to ship.
  • Guest story. The project rule is guest-first (NFR-1): the whole game is playable with no account. PvP is a legitimate account-only extra, which the requirements already allow for ("may gate genuinely online extras"), but the entry point must degrade cleanly when signed out.

Next step: settle the first two questions (what the team is made of, and asynchronous versus live), since every other decision hangs off them. Then a requirements doc in the shape of docs/cloud-sync-requirements.md before any code.

04 Career depth D - in-run economy and node variety A currency during a run, and rounds that are not all "play the tie". Career ▸

The ask (docs/career-depth-spec.md section D, where it is parked as a future idea rather than a spec): give a run an economy and a shape of its own. Two halves that only make sense together.

Form, an in-run currency. Earned from wins and goal margins during a run and spent between rounds on re-rolls, rating heals or an extra boost. It lives and dies with the run, unlike Prestige, which is the career-level currency that survives it. So the run gains a wallet, and a reason to care about a 3-0 over a 1-0.

Node variety. Today every gap between rounds is the same gap: pick 1 of 3 boosts. That is literal rather than a figure of speech, since RunPhase is 'group' | 'boon' | 'match' | 'ended' and the between-round step is boon. Variety rotates it: sometimes a boost pick, sometimes a shop (spend Form), sometimes an event (a themed trade-off choice), sometimes a curse (a genuinely optional high-risk boost).

Why it is wanted. A run is currently five ties and four boost picks, and each pick reduces to taking the biggest number. The spec's own phrasing is that this is what makes the run itself skillful rather than pick-the-biggest-number: the difference between a run being a sequence of decisions and a sequence of results.

Why it is the expensive one. Three costs, in order of nastiness:

  • 1. Temporary effects have nowhere to live. This is the note this item has always carried, and it is exact. Boon.apply is (xi, ctx) => Player[] and RunState.xi is documented as "the current XI, with any boon rating deltas baked in": a boost is applied by rewriting the players, and nothing records what was applied or by how much. So nothing can expire. Two ways out, and only one is sound. An effect ledger beside the XI, with xi recomputed from base plus active effects each round, is the clean fix, and it incidentally settles something domain/challenges.ts already works around: run.xi diverges from the dataset ratings, which is why basePlayer exists. An inverse transform per effect is the tempting one and it is fragile, because the bumps clamp at 99 and so are not reversible: a +2 on a 98 is +1, and the inverse does not know that.
  • 2. The phase machine has to branch. RunPhase grows from four states to about six, and prepareKnockoutRound hard-codes phase: 'boon' with an offer as the thing that follows a tie (run.ts:421). Every consumer changes with it: CupRunScreen's content switch, RunLadder, and the persisted wcsim_run_v1 shape, including a run saved mid-shop having to resume.
  • 3. A second currency has to be balanced against the first. Prestige was sized by simulation: the perk shop plus every locked boost is 2,525, a run pays a median of 9, and the challenge awards were tuned to 2/5/12 against that anchor. Form needs the same treatment. And npm run checks already asserts boost budgets of common 2.0, rare 3.2, legendary 4.5, so a shop that sells rating points has to fit inside those bands or it invalidates the assertion.

What already exists in its favour, which is more than the item's one line suggested:

  • Glass Cannon (+5 to attackers, -3 to defenders) is a working curse template, and it is already exempt from the boost budget check for precisely the reason a curse needs to be: it gives points back.
  • rerollOffer + RunState.rerollsLeft already exist for the Physio Table perk. That is the shop's re-roll item, already built and already persisted.
  • domain/odds.ts is how to judge whether a node's choice is meaningful at all, which is item 05's whole content, so the two are natural companions.

Next step: nothing yet, and deliberately so. Depends on nothing in A/B/C (boost unlocks, tiered perks and Ascension all shipped), but two things bear on it. Every node type is Cup-Run-only machinery piling onto domain/run.ts, the heavier side of the split between the two tournament engines, so building this widens a duplication the hygiene audit deliberately leaves alone and nobody currently owns. And item 27 notes that items 04, 05 and 19 each add a screen the navigation will have to hold, which a shop node and an event node both do. So: land 27, then build this. Building it first means redoing it. When it does start, do the effect ledger as its own step before any node type, since every node type wants it and it is the part that cannot be retrofitted.

24 Signed in, resetting the album (or changing difficulty) blocks the app The account store refuses to clear an album, and the refusal surfaces as the "server unreachable" screen. Two paths reach it, one of them by accident. Accounts ▸

Found 2026-08-20 while auditing for item 23, not in a run, and verified end to end in the code.

remoteStore.clearAlbum() throws on purpose, and its comment gives a good reason: "wiping a synced collection from a settings toggle is a bigger decision than a local reset, and it is what account deletion is for." It then says "the album screen's reset stays guest-only" - and that gating does not exist anywhere. Two paths reach the throw while signed in:

  • The album screen's "Reset album" footer renders unconditionally (AlbumScreen.tsx:236-245), wired straight to stickers.onResetAlbum (App.tsx:839). The player asked for it, so the refusal is at least honest - but the button should not have been offered.
  • Changing the difficulty setting calls the same thing (App.tsx:159-162), with no account check, because stickers are scoped to the difficulty they were earned under. Here the player did not ask to reset anything.

What happens. onResetAlbum sets the in-memory album to empty first, then calls store.clearAlbum(); the throw goes through reporting(), which fires the store-error listener because the session is remote, and App renders the blocking UnreachableScreen over everything (App.tsx:1220-1228). So the screen says the server cannot be reached when the server was never asked, and behind the overlay the album now reads as empty while the account still holds every sticker. A reload restores it, which is the one mercy.

Three ways to fix it, and the choice is a product decision rather than a technical one:

  • Honour the comment. Hide the reset footer when signed in (the album screen would need to know, which it currently does not) and make changeDifficulty skip the album for an account. Cheapest, and it keeps the stated rule. Leaves the difficulty rule inconsistent between guests and accounts.
  • Support it server-side. A reset_album function along execute_trade, since the browser talks to Postgres directly and the sticker economy is validated in security definer functions. Costs a hand-applied migration and a new name, and it is the option that makes the two worlds behave alike.
  • Drop the difficulty-resets-the-album rule and keep the reset button guest-only. This is the broader question of whether the rule should exist at all, since nothing wipes the career or the challenges and those are earned under a difficulty too. Nothing owns that since item 22 was dropped (the audit's off-limits section parks it), so settling it here would be a decision rather than a deferral.

Whatever is chosen, fix the ordering: clear the in-memory album only once the store write has resolved, so a refusal cannot leave the UI disagreeing with the account. And correct the comment in remoteStore, which currently asserts a guard that is not there.

Next step: the first option, as a stopgap, is small and stops a signed-in player hitting a blocking screen from the settings sheet. Decide between the other two together, since both turn on whether the difficulty-resets-the-album rule should exist at all.

26 Wipe the account server for testing Requested: an empty database to test against. The script is written and on main; it needs one command from the LAN or VPN. Accounts ▸

Asked for 2026-08-20. The script exists and is committed; what is left is running it, which needs dkr/.env and reach to the NAS. It is the same route item 25 took on 2026-08-20, so push:sql is proven against this server; only the wipe itself is untried.

The command, dry run first:

npm run push:sql -- --dry-run supabase/maintenance/reset-user-data.sql
npm run push:sql -- supabase/maintenance/reset-user-data.sql

What it deletes. One delete from auth.users does almost all of it: profiles.id references it on delete cascade and every per-user table references profiles the same way, so it takes the album, album stats, career, settings, game state, active run, run results, and the accounts themselves. Sessions and refresh tokens go with them, so anything still signed in falls back to the guest path until it signs in again. audit_log is the exception - it references profiles on delete set null, so its rows survive the cascade with a null user and are deleted explicitly. Keeping the audit trail is one commented-out line in the script.

Three tables must survive, and this is the easy mistake collectibles is generated reference data (npm run gen:collectibles), and finish_run validates every banked sticker id against it - so an empty table makes every run bank nothing while the album silently stops filling, with no error anywhere. economy_constants holds the trade costs and the swap cap, mirrored from src/config.ts. allowed_emails is the retired invite gate. The script touches none of them and ends in a row-count select so the operator can see the user tables at 0 and those two still populated. If collectibles is ever lost, npm run push:collectibles restores it.

It is irreversible, and two accounts hold data (33 run_results rows across them, counted while surveying the dead run_results columns, now the audit's D12). Worth confirming both are the owner's before running it rather than after.

Guest progress is not covered, and cannot be: it is localStorage in a browser, never the server (design decision D8, two worlds never mixed). A device is cleared from its own console, and the script's header carries the snippet for the seven keys. Note wcsim_settings_v1 is listed separately there because a reset deliberately keeps theme, difficulty and year pool.

It cannot undo item 25. Migration 0012 went on 2026-08-20 and a wipe removes rows, not function definitions, so finish_run_v2 keeps the fix however often the user tables are emptied. Worth knowing while testing: a freshly wiped album cannot be full, so the duplicate cup pick 0012 legalised is not reachable again until one is.

Next step: run the dry run, read the row counts it reports, then run it for real and confirm every user table reads 0 while collectibles still reads 81. Then close this item.
