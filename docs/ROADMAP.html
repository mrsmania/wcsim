03 More World Cups and collectibles Extend the dataset backwards from 1990: 1986, 1982, and earlier. Content ▸

The dataset covers 1990 to 2022, all nine fully researched. Collectibles grow for free, since collectibility is derived from rating via STICKER_TIERS.

  • Method notes from the 1990-2002 round apply: identical name spellings across tournaments for the same person (personId is the name slug), distinct people must have distinct names, ratings are that-tournament strength on 60-99.
  • Field sizes shrink going back (24 teams in 1982 and 1986, 16 in 1970-1978), so check the group draw and any "32 nations" assumptions first.
  • Period identities keep their own codes, as Soviet Union, Czechoslovakia and Yugoslavia already do.
  • Remember the server: after any rating change run npm run gen:collectibles then npm run push:collectibles. npm run checks fails while the seed is stale.

Next step: do 1986 end to end as the template for the rest.

15 Point GoTrue at the new sign-in email The template is written and deployed; prod still sends the stock one. Hands-on ▸

The mail itself is done (2026-08-18) and lives in the repo, deployed with the site: public/email/otp.html plus public/email/logo.png. Plain on purpose: the trophy tile and wordmark, one line, the six digits, and a line saying to delete it if it was not you. No greeting, no sign-off, no unsubscribe footer.

Settled while building it. A copy button inside the mail is impossible - mail clients run no JavaScript, and no HTML or CSS writes to the clipboard - so the code is large, letter-spaced and selectable instead, which is what makes tap-and-hold work and what feeds the phone's own one-time-code suggestion (the code field already carries autocomplete="one-time-code"). There is deliberately no link in the mail either: the only placeholder is {{ .Token }}, and the app verifies with verifyOtp({type:'email'}), which takes the code alone. One mail, not two: GoTrue picks a different template slot for a first-time address (confirmation) than for a returning one (magic link), so both slots below point at the same file - that is what makes the two cases identical, and leaving either unset means half the players still get the stock mail.

The manual step, on the prod stack. Everything below happens in the Supabase compose folder on the NAS (the one from docs/nas-setup.md §4, e.g. /volume1/docker/wcsim-supabase), whose .env is the file the repo's gitignored dkr/.env is a copy of.

  1. Add the four values to .env next to docker-compose.yml. No quotes, no spaces around =; compose would treat quotes as part of the value. 
    GOTRUE_MAILER_SUBJECTS_MAGIC_LINK=Your World Cup Simulator code
GOTRUE_MAILER_SUBJECTS_CONFIRMATION=Your World Cup Simulator code
GOTRUE_MAILER_TEMPLATES_MAGIC_LINK=https://mrsmania.github.io/wcsim/email/otp.html
GOTRUE_MAILER_TEMPLATES_CONFIRMATION=https://mrsmania.github.io/wcsim/email/otp.html
  2. Make sure the auth service actually passes them through. This is the step that silently wastes an evening: the official Supabase compose does not hand .env to the container wholesale, it lists an explicit environment: allowlist per service, and the mailer template keys ship commented out. A value sitting in .env that no service references reaches nothing. 
    grep -n MAILER docker-compose.yml
    If the four keys are absent or commented, add them to the auth service's environment: block (indentation matters, two spaces deeper than environment:): 
      auth:
    environment:
      GOTRUE_MAILER_SUBJECTS_MAGIC_LINK: ${GOTRUE_MAILER_SUBJECTS_MAGIC_LINK}
      GOTRUE_MAILER_SUBJECTS_CONFIRMATION: ${GOTRUE_MAILER_SUBJECTS_CONFIRMATION}
      GOTRUE_MAILER_TEMPLATES_MAGIC_LINK: ${GOTRUE_MAILER_TEMPLATES_MAGIC_LINK}
      GOTRUE_MAILER_TEMPLATES_CONFIRMATION: ${GOTRUE_MAILER_TEMPLATES_CONFIRMATION}
    (If that service already has an env_file: .env line, step 1 was enough and this one is a no-op.)
  3. Re-create the container, do not restart it. A container's environment is fixed when it is created, so docker compose restart auth comes back with the old values and looks like the change did nothing. 
    docker compose up -d auth
    In DSM's Container Manager the equivalent is opening the Project and using Action → Build (stop first if it refuses); the label moves between DSM versions, but anything that re-runs compose is right and a plain container Restart is not.
  4. Prove the values are inside the container rather than merely in the file. This is the check that separates "typo in .env" from everything else; expect all four lines back. 
    docker compose exec auth env | grep GOTRUE_MAILER_
  5. Prove the NAS can fetch the template. GoTrue pulls it over HTTPS as it sends, so this has to work from the NAS, not just from your laptop. Expect 200 and an HTML content type for both. 
    curl -sI https://mrsmania.github.io/wcsim/email/otp.html
curl -sI https://mrsmania.github.io/wcsim/email/logo.png
  6. Send yourself a code from the game, signed out, and read it on a phone. Check the subject line as well as the body, because the two carry different diagnoses (next paragraph).

If it still looks stock, the subject line tells you which half failed. Subjects are used verbatim, while the body is fetched, so:

  • Neither changed - the variables never reached the container. Back to steps 2 to 4; almost always the compose allowlist or a plain restart.
  • Subject changed, body still stock - the variables are fine and the template fetch failed, which GoTrue answers by falling back to its built-in default rather than erroring. Check step 5 from the NAS, then the log: 
    docker compose logs --tail=200 auth | grep -i -e template -e mailer -e "unable to"
  • Right layout, no logo - the mail is ours and the image was blocked or unreachable. Blocked is normal (the header still reads); unreachable means the second curl in step 5 fails.

Rollback and upkeep: to go back, delete the four lines (or re-comment them in the compose) and docker compose up -d auth again - nothing else was touched, and no database state is involved. Afterwards, editing the mail is a push to main plus the Pages deploy, with no restart: only these variables need one. Worth mirroring the four lines into the local dkr/.env copy too, so it does not drift from prod.

  • 08 Banking a run costs one round trip, not three. Done 2026-08-18, after profiling rather than guessing - the four candidates had four different fixes and three of them were innocent. Not the deliberate wait: BANK_WAIT_MS caps how long the "Draft a new XI" button reads "Saving stickers...", while the summary renders when the promise resolves. Not the function: measured on a local Postgres running the real migrations and the real 81-row catalogue, finish_run takes 8.8 ms cold and 1.3-1.9 ms warm for a full 11-sticker haul. The write queue contributes one round trip per write already in flight. The cause was that a bank cost three sequential round trips: the call, then a state_version read, then the album plus album_stats - because the function returned only the new ids. Measured client-side against a fake transport at 100 ms/request: 302 ms idle, 502 ms behind two writes. Migration 0010 adds finish_run_v2, which returns the new ids, the version, the album rows and the stats computed in the same transaction, so the client's "the server counted, do not guess" rule is intact and the bank is one trip: 1 wave instead of 3, and 3 instead of 5 behind two writes. A new name rather than a changed return type because the client ships on push to main while the migration is applied by hand on the NAS: the client tries v2, falls back to the old path once per session if the server has not been migrated, and never falls back on a real error (PostgREST answers a missing function with PGRST202 before Postgres runs anything, so the retry is a first attempt and not a double submit). The old finish_run stays as a thin wrapper delegating to v2, so there is still one implementation. Applying it on the NAS is open item 16.
