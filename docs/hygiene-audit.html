World Cup Simulator

Hygiene dead code and refactoring backlog

Audited: 2026-08-20
Status: backlog, not started
Roadmap: item 23

What this is. A worked list of dead code and behaviour-preserving refactorings across the whole codebase, judged against DRY, KISS, SoC and YAGNI. It is written to be executed, in waves, by a team that was not in the room when it was written: every entry names the files, the fix, whether it changes behaviour, effort and risk.

The single rule. No change in functionality. The app that comes out plays exactly like the app that went in. Where an item cannot honour that, it says so and is parked in Decisions instead of being smuggled in as a cleanup.

The gate. npm run build clean and npm run checks at 59/59, verified green on main at 2026-08-20 before any of this. There is no unit-test runner, so those two plus reading the diff are the whole safety net. That is why wave 7 puts npm run checks into CI first.

How it was produced. Six independent reviews of the tree in parallel: dead weight, DRY, SoC/layering, KISS/YAGNI, type model and naming, and tooling/SQL/assets. Overlaps were merged and the load-bearing claims re-verified by hand. Roughly 190 findings survived.

Do not start before roadmap item 27 has flipped its default

Item 27 (the navigation and click-path rework) moves the same code this backlog touches: App.tsx's route branch, the mode fact being derived twice, the reset target, the two nav cards in the build page's left column, and the career hub splitting off the run screen. Doing hygiene first means doing several of these twice, and the second pass would be the one that loses.

Updated 2026-08-21: item 27's chrome has landed, but as a PREVIEW, not as the default. Concept 2 (five tabs) is implemented behind a runtime switch (?nav=tabs, src/nav/navMode.ts), so App.tsx now carries both chromes: the classic route branch, footer nav, two build routes and modeOfPath, alongside the TABS branches, /play, /career, /records and the run-kind control. That makes this callout more binding rather than less: refactoring either path now means doing it twice, and one of the two is about to be deleted. The block lifts when the default flips and the losing chrome goes - not when the preview shipped.

Updated 2026-08-20: this callout used to name roadmap item 22, which has been dropped. Its navigational half is item 27's. The rest of what it owned (the two tournament engines, the two chemistry definitions, the run-end sticker trigger order, the difficulty-resets-the-album rule, whether a non-career run pays) now has no owner, and is still not this backlog's to settle, because none of it is behaviour-preserving.

The Off limits section says which is which. Everything else here is independent of both.

Ground rules for the implementing team

  1. One wave per branch, one item per commit (or one commit per tight group of identical mechanical edits, e.g. "un-export 12 symbols"). A 40-file wave in one commit cannot be reviewed, and this whole backlog is only worth doing if the diffs are reviewable.
  2. Run the gate before every commit. npm run build always; npm run checks whenever the commit touches src/domain/ or scripts/. Both are fast (build ~4s, checks ~14s).
  3. Never reformat as a side effect. 2-space indent, match the surrounding file. If a file is the wrong width, that is its own commit (see H17), not a rider on a logic change.
  4. No em-dashes in anything you write, including commit messages and comments. "rating" not elo, "boost" not boon, in any user-visible string.
  5. If an item turns out to be wrong, stop and say so. Every claim below was verified once, but a claim can rot between the audit and the work. A finding that no longer reproduces is a finding about this document, not a licence to improvise a different change.
  6. Behaviour-preserving means observably identical, including the things that are easy to forget: aria-label text, the order of a rendered list, what a title tooltip says, which element receives focus, and what lands in localStorage. Anything persisted is a compatibility surface: a renamed field in wcsim_run_v1 or the active_run.data blob breaks a run in progress unless the loader tolerates both spellings.
  7. Deleting an export is not free if scripts/checks.ts imports it. The harness is the only test suite; keep it compiling and keep its coverage.

Principle tags used below: dead dry kiss soc yagni. Effort is S (under an hour), M (a sitting), L (its own piece of work). Rows shaded amber need an owner decision first and are cross-linked to Decisions.

D12The four dead columns on run_results: drop them or revive them? Merged in from roadmap item 21 on 2026-08-20, which was closed as a duplicate of this table rather than of the waves: it was always a decision, never a refactor. run_results was created by 0001 as a genuine per-run archive and populated in full by 0003. 0006_client_surface.sql then narrowed the function deliberately and says why in its own header: banking stickers and computing the career award turned out to be two moments in two places, so finish_run kept everything that protects the collection and handed the career award back to the client. The career facts stopped being passed and the columns holding them went quiet; 0009 and 0010 carried the narrowed insert forward. Confirmed against the live server, not just the migrations: neither finish_run nor finish_run_v2 takes an ascension, score, rounds-won or XI argument, so the client cannot send them even in principle. The insert is (user_id, run_key, outcome, won_cup, xi) with xi a literal '[]'::jsonb and the rest taking their defaults; across 33 rows from two accounts, ascension > 0 matches nothing. The table itself must not be dropped: its unique (user_id, run_key) is what rejects a double submit before a single sticker moves, and import_guest_progress reads it to decide whether an account is empty. Only the four columns are dead weight. Drop them and the next person stops building on a column that is always 0, which is what item 06 nearly did. Revive them and the table becomes real per-run history, answering "runs finished at Ascension II" retroactively and founding any server-side leaderboard - but the trophy cabinet no longer needs it (item 06 shipped its archive on CareerStats, riding the existing save_career jsonb, so it works for guests too, and guest-first is the project rule), and it costs a new function name (finish_run_v3), since a changed signature has the same PGRST202 problem a changed return shape had while migrations are applied by hand and the client ships on push to main. Either way it only ever covers runs from the change onward: the rows already there cannot be back-filled, because the facts were never sent. Account-only in all cases; guests write nothing to the server. Files: supabase/migrations/{0001_schema,0006_client_surface,0010_finish_run_one_trip}.sql, src/state/store/remoteStore.ts.
