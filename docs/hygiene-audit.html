What this is. A worked list of dead code and behaviour-preserving refactorings across the whole codebase, judged against DRY, KISS, SoC and YAGNI. It is written to be executed, in waves, by a team that was not in the room when it was written: every entry names the files, the fix, whether it changes behaviour, effort and risk.

The single rule. No change in functionality. The app that comes out plays exactly like the app that went in. Where an item cannot honour that, it says so and is parked in Decisions instead of being smuggled in as a cleanup.

Why it was redone. The first pass was produced on 2026-08-20 against commit 5a22fca. Fifty commits landed after it and before any of it was executed, moving 5,262 lines and deleting 2,160 in src/ - items 27, 28, 29, 31 and 32, which deleted a whole tournament mode, the old navigation chrome and five boost cards. That is enough drift that the old document could not be handed to an implementer: of its 105 items, 7 were flatly wrong, 24 had shrunk, 1 was already done by deletion, and a dozen published counts were out by material margins. This pass re-ran the same method and reconciled every old item against the tree as it is now.

How it was produced. Six independent parallel reviews of the tree - dead weight, DRY, SoC/layering, KISS/YAGNI, type model and naming, tooling/SQL/assets - plus two passes re-verifying the old backlog item by item. Overlaps were merged and the load-bearing claims re-verified by hand, including four mutation tests against the checks harness.

The gate. npm run build clean and npm run checks at 132 invariants. There is no unit-test runner, so those two plus reading the diff are the whole safety net - and as of 2026-08-24 both run in CI (H91), which they did not when this audit was written. The stop block below records what was wrong with the harness and what was done about it; read it before trusting a green suite from before that date.

Start here — the safety net has a hole in it

npm run checks fails at random again, and one of its checks guards nothing. Both were measured on clean main at c4f1512, and together they mean the gate this backlog leans on is weaker than its 132/132 suggests. Fix these before executing anything else, in this order:

1. The suite is flaky, about one run in twelve (H106). Observed 2 failures in 11 consecutive runs, always the same check: boons: the Extra Choice perk adds one offer card per owned tier. Root cause measured, and it is not the perk: the check plays a real group stage and then reads the boost offer, which only exists if the user qualified. When ger-1990's best XI goes out in the group the offer is undefined, the size test reads 0 against an expected 4 or 5, and the check fails. Per tier that is 4.4% and 3.7% over 2,000 runs each, so roughly 8% per suite. This is the third instance of the same bug class that roadmap item 31 closed on 2026-08-23 with "0 failures in 3000 runs" - a threshold sitting inside its own distribution.

2. It is a hard prerequisite for H91. Putting a suite that fails 8% of the time into CI trains everyone to re-run it, which is worse than not having it. H91 is still the right first move; H106 is now the move before it.

3. One check is vacuous, and it is the one guarding a known exploit (H107). prime-years samples bestEleven(SQUADS[0].players) = ger-1990, which is one of 60 of 272 squads where Prime Years finds no upgrade at all. So arrived is empty and the loop asserting "every arrival is tagged" iterates zero times. Verified by reintroducing the exact historical bug it exists to catch - grantBoon recording only the first arrival, so ten handed 90+ players bank stickers they were given - and the suite still reported 132 passed, 0 failed.

Ground rules for the implementing team

  1. One wave per branch, one item per commit (or one commit per tight group of identical mechanical edits, e.g. "un-export 12 symbols"). A 40-file wave in one commit cannot be reviewed, and this whole backlog is only worth doing if the diffs are reviewable.
  2. Run the gate before every commit. npm run build always; npm run checks whenever the commit touches src/domain/ or scripts/. Measured at this commit: build 10.5s, checks 16.9s.
  3. Re-verify the item before you start it. This is the lesson of the first pass: it sat for four days, the tree moved under it, and 32 of its 105 items had to be corrected or withdrawn. Every claim here was verified on 2026-08-24; a claim that no longer reproduces is a finding about this document, not a licence to improvise a different change.
  4. Never reformat as a side effect. 2-space indent, match the surrounding file. 17 of 58 source files are 4-space, deliberately; a width change is its own commit, never a rider.
  5. No em-dashes in anything you write, including commit messages and comments. "rating" not elo, "boost" not boon, in any user-visible string.
  6. Behaviour-preserving means observably identical, including the things that are easy to forget: aria-label text, the order of a rendered list, what a title tooltip says, which element receives focus, and what lands in localStorage. Anything persisted is a compatibility surface.
  7. But note the standing exception: CLAUDE.md records that there are no production users yet, so breaking a persisted shape is a free choice rather than a migration. Several items below turn on that - they are grouped as D13 so they are decided once rather than eleven times.
  8. Deleting an export is not free if scripts/checks.ts imports it. The harness is the only test suite; keep it compiling and keep its coverage. Two items in the first pass (H1, H11) would now break the build if executed as written, because code added since gave both symbols a real consumer.
